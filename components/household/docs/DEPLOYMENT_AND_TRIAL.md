For version 3.2 deployment, README.md, SECURITY_AND_RESIDUAL_RISK.md, GAP_CLOSURE.md, PHONE_AND_PUSH.md and MAIL_AND_OAUTH.md override obsolete statements about unavailable features. The following describes the inherited component; its historical test totals are not this release's totals.

# Deployment sequence, not a claim of deployment

1. Verify candidate and parent identities. Run the tests into directories OUTSIDE the package. Preserve all existing work and real state. No accounts are needed for this stage.
2. Start the household-only local demonstration on loopback using existing Python. Record an actual browser result, including access blocks. Do not bypass those blocks.
3. When explicitly authorized and existing TLS/network prerequisites are satisfied, use the private phone trial. Keep the calendar writer disabled. Complete the phone receipt with actual device/browser evidence.
4. Test a benign private routine through cue, original-context Done/snooze, disconnection, reconnection, deduplication and a real day boundary. Test app closure separately. Report foreground success separately from unsupported background push.
5. Only after household trial review, perform one specifically approved Google canary with a trusted operator/account setup. Verify account identity, private audience, If-Match, reminder preservation and original-provider recovery. An account canary is not permission to manage all appointments.
6. Review email ingestion and scheduling separately through actual supported connectors. Do not claim source coverage or scheduled execution from a ZIP. No cloud task or system service is installed by this candidate.

The next release gate is actual private-device usefulness, not additional architectural expansion. Use config/PHONE_TRIAL_RECEIPT_TEMPLATE.json and config/DEPLOYMENT_RECEIPT_TEMPLATE.json. All live fields initially NOT_ESTABLISHED/NOT_RUN.
